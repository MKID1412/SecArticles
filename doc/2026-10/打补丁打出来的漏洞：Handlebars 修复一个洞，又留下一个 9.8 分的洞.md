2026 年 10 月 6 日奇安信 CERT 原创发现 Handlebars.js 模板引擎存在 CVSS 9.8 远程代码执行漏洞，影响 4.0.0–4.7.9 全系列。本文给出企业 3 步走防御路径，从版本升级到代码侧加固切断原型链穿透。  
  
Handlebars.js 不是"前端模板"那么简单——它是大量企业报表系统、邮件系统、通知系统的事实标配。这次漏洞源自上一版修复 CVE-2026-33937 时新引入的校验器的回归失守，是 2026 年典型补丁史的代表案例。

二、漏洞原理  
  
Handlebars 是一款被广泛使用的开源 JavaScript 语义模板引擎，覆盖服务端 Node.js 渲染与浏览器渲染两个场景，是大量报表系统、邮件模板、通知系统、营销活动页、自研低代码平台的事实标配。下面只描述机制层，不输出可利用的 AST 构造。  
  
环节 A：4.7.9 引入的"修复器"  
  
2026 年 CVE-2026-33937 披露后，Handlebars 维护者在 4.7.9 版本引入 validateAstNode 校验器，用于对抗 AST 类型混淆导致的 JavaScript 注入。这是一次方向正确的修复。  
  
环节 B：校验器的检查范围"漏掉了一层"  
  
validateAstNode 在遍历节点时使用的是   
Object.keys()——它只读取对象的自有可枚举属性。而下游负责把 AST 编译为可执行 JavaScript 的代码生成器，用的是  
普通属性访问——会沿  
原型链一路向上读字段。两者检查范围不一致。  
  
环节 C：原型"挂"攻击  
  
攻击者无需构造一个"完整看起来合理"的 AST 对象。  
把整个恶意 Program AST 挂到传入 compile() 的对象的原型上——例如 Object.create(maliciousTemplate) 或带原型污染的深合并结果。校验器那边看到的是"一个几乎为空的对象（自有属性都被遮蔽）"，视为通过；编译器那边照常按原型链找到那些恶意字段，照常编译并执行。  
  
环节 D：调用入口决定爆炸半径  
  
漏洞本身不出在 Handlebars，  
出在"把用户输入喂给 Handlebars"的代码模式：Object.assign({}, userJson)、Object.create(userObj) 后立即 compile()；lodash.merge / defaultsDeep 等深合并后再 compile()；任何"先合并 → 后编译"模板 API 都属于这一类。  
  
为什么"原型链"是这次的致命放大器？  
  
JavaScript 原型链是这门语言的基础机制。它在大多数业务里毫无存在感，但在  
"两个代码用同一份数据但读法不同"的场景里，会出现"防御逻辑认为数据干净、实际执行逻辑被数据污染"的失配。CVE-2026-106446 是这一失配的教科书级案例——校验器是补丁引入的，意味着传统"补丁 = 安全"的直觉会反向：打了补丁的系统反而带着校验器上线，补丁本身变成了攻击面。  
  
容器化场景下，Node 进程若以 root 权限运行，攻击者一旦进入容器，对宿主机的渗透路径与任意 RCE 等同。

五、处置步骤  
  
第一步，资产盘点（24 小时内）。用 npm ls handlebars / pnpm why handlebars / SCA 工具全网扫描 4.0.0 ≤ V < 4.7.10，出表单给到对应业务负责人；包含经 Object.assign / Object.create / lodash.merge 再 compile() 的代码片段统计。  
  
第二步，版本升级（72 小时内）。所有受影响项目升 handlebars@4.7.10 或更高，CI 流水线加 <4.7.10 的硬阻断；升级时同时做一次"邮件 / 通知 / 报表"端到端回归渲染。  
  
第三步，代码侧加固。把"用户输入 → 模板上下文"的透传链路重新收敛——只接受白名单字段、对入参做 JSON.parse(JSON.stringify(obj)) 切断原型链、或用 Object.create(null) 作为编译目标对象；SAST 规则加一条"Object.assign 后立刻传入 compile/precompile"报警。  
  
第四步，容器与运行时。扫描所有基于受影响 Handlebars 的容器镜像，确认 Node 进程不以 root 运行；sidecar 流量做异常监测；EDR 对非常规父进程发起的 child_process.exec 加大告警权重。  
  
第五步，持续监控 + 应急取信。PoC/EXP 已公开意味着攻击前窗已打开，7 日内每天做一次"代码侧 grep + 版本回归"复核；保留官方公告页（奇安信 CERT / Handlebars 官方仓库 release）作为应急取信单一入口。  
  
六、几点判断  
  
"打补丁打出来的漏洞"是 2026 年的一种典型补丁史。4.7.9 引入的校验器是修上一洞；4.7.10 是修这一洞。研发型/外包型企业的标准补丁史里，类似回归失守会持续刷新。补丁管理不再是"打一行就完事"，而是要建立"上版本差异 vs 下版本差异 vs 攻击面变化"的三件套对账。  
  
Handlebars 不是"前端模板"——它是企业最隐蔽的内网入口。报表、邮件、通知、自研低代码，全部走 Handlebars。一处洞覆盖十几个业务线，SCA 工具的依赖清单必须把它标记为"高暴露面组件"，不能再简单按开源模板分类。  
  
容器化把 Server-side Template Injection 抬上了一个台阶。上一个 RCE 影响的是业务；这次 RCE 影响的是宿主机。容器安全、网络出口最小权限、Node 进程降权——这些原本归到"基础设施"的事，从今天起要并入 SCA 升级同一份作战图。
