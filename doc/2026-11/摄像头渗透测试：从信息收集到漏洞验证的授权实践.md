#  摄像头渗透测试：从信息收集到漏洞验证的授权实践  
原创 暗夜铭少

## 1. 引言  
  
随着视频监控设备大规模接入网络，摄像头已经成为物联网中数量最多、暴露面最广的一类终端。很多设备出厂默认开启 Web 管理、Telnet、ONVIF 等服务，固件更新滞后，弱口令与已知漏洞长期存在，因此摄像头也成了渗透测试与攻防演练中的常见目标。  
  
![](https://mmbiz.qpic.cn/mmbiz_png/VqJrJwib7Fo0iav73kj4te8o1sDT9DU3NLN4gG4ncffZnphREiaHiccZh5mHSfYC9bSTCMKWtSEjzDHpvicd7J97GIIDAeDGzqEhyicGk8ffgTvib0/640?wx_fmt=png&from=appmsg "")  
  
本文从**授权测试**  
的角度出发，梳理摄像头渗透测试的完整流程：信息收集、服务识别、认证测试、漏洞验证与加固建议。文中所有技术点仅用于**自有设备或已获得书面授权的资产**  
，请勿用于任何未授权目标。  
> 法律提示：未经授权对他人设备进行扫描、爆破或漏洞利用，可能触犯《网络安全法》《刑法》相关规定。测试前务必确认授权范围、时间窗口与应急联系人。  
  
## 2. 测试前的准备与授权  
### 2.1 授权与范围确认  
- • 明确授权主体、目标 IP/域名清单、测试时间段；  
  
- • 约定禁止操作（如禁止导致设备重启、禁止修改固件、禁止导出真实监控画面）；  
  
- • 准备应急回滚方案，避免测试导致业务中断。

## 3. 信息收集与资产发现  
### 3.1 主机与服务发现  
```
# 快速发现存活主机与常见摄像头端口
nmap -sn 192.168.1.0/24

# 针对单台设备做服务与版本识别
nmap -sV -p 80,443,554,8554,8080,37777,23,22 192.168.1.100
```  
  
摄像头常见端口：  
- • 80/443  
：Web 管理界面  
  
- • 554/8554  
：RTSP 视频流  
  
- • 37777  
：大华设备私有协议  
  
- • 8000/8080  
：部分厂商 Web 或 SDK 服务  
  
- • 23/22  
：Telnet / SSH 管理  
  
### 3.2 指纹识别  
  
通过 HTTP 响应头、页面标题、favicon 哈希、Server  
 字段等识别厂商与型号：  
```
curl -I http://192.168.1.100/
curl -s http://192.168.1.100/ | grep -i -E "title|server"
```  
  
常见指纹特征包括 Server: Boa/0.94.14rc21  
（部分海康设备）、App-webs  
、Dahua  
 等关键字。识别出厂商与固件版本后，可对照厂商安全公告与 CVE 列表判断是否存在已知问题。

favicon 哈希是一种稳定性较高的指纹：同一厂商不同型号常复用同一图标，因此哈希值往往能直接对应到厂商甚至设备系列。采集时先下载图标文件，再用 mmh3 计算哈希（Shodan 与 Fofa 均采用 mmh3 的有符号整数结果）：  
```
# 下载 favicon 并计算 mmh3 哈希
curl -s http://192.168.1.100/favicon.ico -o favicon.ico
python3 -c "import mmh3; data=open('favicon.ico','rb').read(); print(mmh3.hash(data))"
```  
  
拿到哈希后，可在授权范围内用空间测绘平台交叉验证。Shodan 语法为 http.favicon.hash:-1234567890  
，Fofa 语法为 icon_hash="-1234567890"  
，将哈希值替换为实际计算结果即可。若检索结果中出现大量同厂商设备，且 Server  
、页面标题等特征与本地采集一致，即可较高置信度地判定厂商与型号；反之若哈希无匹配结果，则说明该图标为定制或新版本，需要结合 Server  
 头、登录页路径与协议 Banner 综合判断，避免仅凭单一指纹下结论。  
### 3.3 搜索引擎与空间测绘  
  
在授权范围内，可借助 Shodan、Fofa、ZoomEye 等空间测绘平台核对资产暴露情况，确认是否存在未在清单中的旁路入口。  
## 4. 认证与访问控制测试  
### 4.1 默认与弱口令  
  
很多设备出厂存在默认账号，或允许简单口令。测试时应在授权范围内、控制请求频率，避免触发设备锁定：  
- • 核对厂商文档中的默认账号是否已被修改；  
  
- • 检查是否存在空口令、纯数字口令等弱口令策略；  
  
- • 关注登录失败次数限制、验证码、锁定机制是否生效。  
  
### 4.2 认证绕过与越权  
- • 检查管理接口是否存在未授权访问（如直接请求 /config  
、/api/...  
 返回敏感数据）；  
  
- • 测试会话 Cookie / Token 是否可预测、是否缺少 HttpOnly 与 Secure 属性；  
  
- • 验证普通用户与管理员权限边界，是否存在水平/垂直越权。  
  
### 4.3 传输安全  
- • 是否强制 HTTPS，是否存在自签名证书与弱加密套件；  
  
- • RTSP 流是否可被未认证访问（部分设备 RTSP 无需认证即可拉流，属于高风险项）。  
  
#### RTSP 未授权拉流验证示例  
  
RTSP 未认证访问是摄像头最常见的高风险问题之一。验证时只需确认「不带凭据能否建立会话并取到视频流」，**不要长时间拉流、不要保存真实画面**  
，仅以能否建立会话作为判定依据。  
  
使用 curl  
 探测 RTSP 是否需要认证（-I  
 只做 OPTIONS/DESCRIBE 交互，不实际拉流）：  
```
# 不带任何凭据请求 RTSP 资源
curl -s -I -X OPTIONS rtsp://192.168.1.100:554/Streaming/Channels/101

# 尝试 DESCRIBE，观察是否返回 SDP 描述
curl -s -X DESCRIBE rtsp://192.168.1.100:554/Streaming/Channels/101
```  
  
使用 ffprobe  
 更直观地判断是否需要认证（只读取流信息，不落盘）：  
```
# 不带凭据探测流信息，超时 5 秒，避免长时间占用
ffprobe -rtsp_transport tcp -timeout 5000000 \
  rtsp://192.168.1.100:554/Streaming/Channels/101
```  
  
预期输出说明：  
- • **需要认证**  
：curl  
 返回 401 Unauthorized  
，响应头含 WWW-Authenticate: Basic realm="..."  
 或 Digest  
；ffprobe  
 报错类似 method DESCRIBE failed: 401 Unauthorized  
，无法获取流信息。  
  
- • **未授权可访问**  
：curl  
 返回 200 OK  
 并带有 Public: OPTIONS, DESCRIBE, SETUP, PLAY, ...  
 等方法列表；ffprobe  
 正常输出 Stream #0:0  
、Video: h264  
、分辨率与帧率等 SDP 信息，说明无需凭据即可建立会话。  
  
判定为高风险的条件（满足任一即可）：  
- • 不带凭据即可完成 DESCRIBE  
 并返回有效 SDP，且 SETUP  
/PLAY  
 能建立会话；  
  
- • 视频流为明文 RTP 传输（非 SRTP），可被同网段抓包还原画面；  
  
- • 设备同时将 554 端口直接暴露在公网，且无来源 IP 限制。  
  
> 注意：以上命令仅可在**自有设备或已获得书面授权的资产**  
上执行。验证时控制并发与时长，避免影响正常监控业务；如发现未授权拉流，应记录请求与响应作为证据，并立即在报告中标注为高风险项，切勿导出或传播真实监控画面。  
  
## 5. 常见漏洞类型与验证思路  
### 5.1 命令注入  
  
部分设备的 CGI 接口对参数过滤不严，存在命令注入。验证时使用**无害命令**  
（如 id  
、whoami  
）确认回显，禁止执行破坏性操作。  
### 5.2 路径穿越与任意文件读取  
  
检查 Web 接口是否可通过 ../  
 读取配置文件、日志或凭据文件。验证时仅读取必要的最小文件，并做好记录。  
### 5.3 缓冲区溢出与固件漏洞  
  
部分老型号在 ONVIF、私有协议处理中存在溢出漏洞。此类验证风险较高，建议在实验环境复现，生产环境仅做版本比对与公告核对。  
### 5.4 未授权访问与信息泄露  
- • 未认证即可访问的配置接口、调试页面；  
  
- • 日志、备份文件、固件下载链接暴露；  
  
- • 视频流未加密、可被任意拉取。  
  
### 5.5 固件与供应链风险  
- • 固件是否可被下载并解包分析（binwalk）；  
  
- • 是否存在硬编码密钥、后门账号；  
  
- • 第三方组件是否存在已知 CVE。

## 7. 加固与防护建议  
- • **修改默认口令**  
，启用强口令策略与登录失败锁定；  
  
- • **关闭不必要的服务**  
（Telnet、未使用的 Web 端口、调试接口）；  
  
- • **及时升级固件**  
，关注厂商安全公告；  
  
- • **网络隔离**  
：将摄像头划分到独立 VLAN，禁止直接暴露公网；  
  
- • **访问控制**  
：限制管理界面来源 IP，启用 HTTPS 与强加密；  
  
- • **监控与审计**  
：开启日志，接入流量监测，及时发现异常登录与拉流行为。  
  
## 8. 总结  
  
摄像头渗透测试的核心不是“拿到 shell”，而是**在授权范围内系统性地验证风险、量化影响并给出可落地的加固方案**  
。从资产发现、指纹识别到认证测试与漏洞验证，每一步都应遵循最小影响原则，做好记录与回滚准备。对设备厂商而言，默认安全、及时更新与最小暴露面，才是降低摄像头整体风险的根本手段。
